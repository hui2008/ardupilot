# Duff RC Output Notes

The Duff Linux board uses `RCOutput_Duff` as its RC output backend. This
backend generates software PWM on Raspberry Pi BCM GPIO18, which is physical
pin 12.

## Output Channel Mapping

`RCOutput_Duff` does not decide which high-level function uses the output.
ArduPilot decides that earlier through the `SERVOx_FUNCTION` parameters.

The high-level output path is:

1. Vehicle or motor code writes a function output, such as `Motor1`.
2. `SRV_Channels` maps that function to a physical output, such as `SERVO1`.
3. `SRV_Channel::output_ch()` calls `hal.rcout->write(ch_num, output_pwm)`.
4. `RCOutput_Duff::write()` receives the zero-based channel number and PWM value.

The physical output indices are zero-based:

| Parameter | HAL channel |
|-----------|-------------|
| `SERVO1_FUNCTION` | `0` |
| `SERVO2_FUNCTION` | `1` |
| `SERVO3_FUNCTION` | `2` |

The current experimental Duff backend does not filter on the HAL channel. It
prints the channel passed by the caller and drives the single GPIO18 output with
the most recent PWM value. This means `SERVO1`, `SERVO2`, or any other mapped
function can be observed without changing the driver.

There is still only one physical output. If multiple logical channels write to
the backend, the last write wins and controls GPIO18.

## Board Default Parameters

Linux board-specific default parameters are not configured in `hwdef.dat`.
They are stored in:

```text
libraries/AP_HAL_Linux/boards/<board>/defaults.parm
```

For Duff, the defaults file is:

```text
libraries/AP_HAL_Linux/boards/duff/defaults.parm
```

The current Duff default is:

```text
SERVO1_FUNCTION 33
```

Function `33` is `Motor1`, so this maps Copter `Motor1` to `SERVO1`, which
means the high-level caller passes channel `0` to `RCOutput_Duff`. The
experimental backend would also accept other channel numbers and send their PWM
values to GPIO18.

If the board should instead default to Plane or Rover throttle output, use:

```text
SERVO1_FUNCTION 70
```

Function `70` is `Throttle`.

## Why `SERVOx_FUNCTION` Is Not A C++ Symbol

`SERVOx_FUNCTION` is a runtime parameter name generated by ArduPilot's parameter
metadata. It is not defined as a literal C++ variable, enum, or macro.

Each individual servo channel defines a generic `FUNCTION` parameter in
`SRV_Channel`:

```cpp
AP_GROUPINFO("FUNCTION", 5, SRV_Channel, function, 0),
```

`SRV_Channels` then exposes an array of `SRV_Channel` objects as numbered
subgroups:

```cpp
AP_SUBGROUPINFO(obj_channels[0], "1_", 1, SRV_Channels, SRV_Channel),
AP_SUBGROUPINFO(obj_channels[1], "2_", 2, SRV_Channels, SRV_Channel),
```

The parameter system combines the outer `SERVO` group, the channel subgroup
prefix, and the inner `FUNCTION` parameter name:

| Pieces | Runtime parameter |
|--------|-------------------|
| `SERVO` + `1_` + `FUNCTION` | `SERVO1_FUNCTION` |
| `SERVO` + `2_` + `FUNCTION` | `SERVO2_FUNCTION` |
| `SERVO` + `3_` + `FUNCTION` | `SERVO3_FUNCTION` |

That is why searching for a C++ symbol named `SERVO1_FUNCTION` will not find one.
The stored field is `SRV_Channel::function`; `SERVO1_FUNCTION` is the user-facing
parameter name generated for channel 1.

## PWM Values

The caller passes PWM pulse widths in microseconds. The `_us` suffix in names
such as `_pwm_us`, `period_us`, `frame_us`, `high_us`, and `low_us` means
microseconds.

Typical servo or ESC PWM values are:

| PWM value | Meaning |
|-----------|---------|
| `1000 us` | minimum output |
| `1500 us` | neutral or mid output |
| `2000 us` | maximum output |

`RCOutput_Duff::write()` constrains output to `1000..2000 us`.

## Atomic Load And Store

`_pwm_us` is an atomic value:

```cpp
std::atomic<uint16_t> _pwm_us { DEFAULT_PWM_US };
```

It is shared by two threads:

| Thread | Operation |
|--------|-----------|
| Main ArduPilot/control thread | calls `_pwm_us.store(...)` from `write()` |
| Duff PWM worker pthread | calls `_pwm_us.load()` from `pwm_loop()` |

`store()` writes the latest requested pulse width:

```cpp
_pwm_us.store(constrain_uint16(period_us, MIN_PWM_US, MAX_PWM_US));
```

`load()` reads the latest requested pulse width:

```cpp
const uint32_t high_us = MIN(uint32_t(_pwm_us.load()), frame_us);
```

The value is atomic because one thread writes it while another thread reads it.
Using `std::atomic` avoids a C++ data race without adding a mutex to the timing
loop. It does not queue PWM values; the PWM worker simply uses the most recent
value available when it starts each frame.

## Duff Driver Behavior

`RCOutput_Duff::init()` configures GPIO18 as an output, drives it low, and starts
a background pthread. The pthread runs `pwm_loop()`.

When output is disabled, the loop keeps GPIO18 low and sleeps for 20 ms. When
enabled, it:

1. Loads the current frequency.
2. Converts frequency to a frame length in microseconds.
3. Loads the current PWM pulse width.
4. Drives GPIO18 high for the requested high time.
5. Drives GPIO18 low for the rest of the frame.

The frequency is constrained to `1..400 Hz`, and the default is `50 Hz`.

## Why `write()` Does Not Generate The Pulse Directly

`RCOutput_Duff::write()` only stores the latest desired PWM pulse width. It does
not drive GPIO18 high and low directly from inside `write()`.

That follows the normal ArduPilot RCOutput pattern:

| Backend | What `write()` does | What generates timing |
|---------|---------------------|-----------------------|
| Linux `RCOutput_Sysfs` | sets or queues duty cycle | Linux PWM sysfs driver |
| Linux `RCOutput_PRU` | writes period data to PRU shared memory | PRU firmware |
| ChibiOS `RCOutput` | updates `period[]` or `period_corked[]` | timer hardware and `push_local()` |
| SITL `RCOutput` | updates simulated output state | simulator state update |
| Duff `RCOutput_Duff` | stores `_pwm_us` | background `pwm_loop()` pthread |

So the common pattern is:

```text
write() = update the desired output value
hardware, firmware, timer, simulator, or worker thread = produce the output
```

For Duff, GPIO18 is being bit-banged as software PWM. There is no Linux PWM
device, PRU, or hardware timer behind this backend, so `pwm_loop()` acts as the
timing engine.

Generating the pulse directly inside `write()` would be a poor fit because:

1. `write()` would need to sleep for the high and low portions of the frame.
2. At 50 Hz that could block the caller for up to about 20 ms.
3. The waveform would depend on when higher-level code happens to call `write()`.
4. The output would not be a continuous repeated PWM signal unless `write()` was
   called continuously at the correct rate.

Keeping `write()` fast and letting `pwm_loop()` continuously repeat the latest
stored value better matches ArduPilot's RCOutput structure.

## Build Verification

The Duff board defaults file is embedded by waf during the Linux board build.
This was verified with:

```sh
./waf configure --board duff
./waf copter
```

The build output included:

```text
Embedding file defaults.parm:libraries/AP_HAL_Linux/boards/duff/defaults.parm
```
